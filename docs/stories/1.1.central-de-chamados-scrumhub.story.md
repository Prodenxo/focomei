# Story 1.1: Central de Chamados ScrumHub

**Status:** InProgress

## Story

Como usuário autenticado do FocoMEI,
quero uma central de chamados vinculada à minha conta, com leitura e resposta de comentários, badge de não lidos e aviso por WhatsApp quando a equipe comentar ou concluir o ticket,
para acompanhar o suporte sem acessar o ScrumHub e sem perder atualizações da equipe.

---

## Contexto / Descrição

O FocoMEI já abre chamados via ScrumHub (projeto 39), mas o app não oferece lista, conversa, leitura nem avisos posteriores. O ScrumHub não oferece webhook; a sincronização deve ser polling idempotente no backend.

O FocoMEI permanece backend intermediário: o app nunca acessa o ScrumHub diretamente. Vínculos seguros `usuário/empresa → ticket ScrumHub` e eventos de notificação ficam no banco local. Comentários continuam como fonte da verdade no ScrumHub e são carregados via proxy autenticado.

**Pré-requisito de segurança do plano:** rotacionar imediatamente a API Key exposta e configurar a nova somente em `SCRUMHUB_API_KEY` no backend; nunca enviá-la ao frontend.

---

## Acceptance Criteria

### AC1 — Rotação e isolamento da API Key

**Given** a API Key do ScrumHub foi exposta
**When** a implementação for entregue
**Then** a chave nova existe somente em `SCRUMHUB_API_KEY` no backend
**And** o frontend nunca recebe nem embute essa chave.

### AC2 — Proxy autenticado (lista, detalhe, timeline, comentário, leitura)

**Given** um usuário autenticado
**When** ele lista, abre detalhe/timeline, responde um comentário ou marca eventos como lidos
**Then** o backend usa o contexto autenticado (nome, e-mail, telefone, `user_id`, `empresa_id`) e não confia nesses campos enviados pelo cliente
**And** a resposta lista somente os chamados vinculados a esse usuário
**And** o comentário no ScrumHub é publicado com a identidade do solicitante validada no servidor
**And** o contador de não lidos é retornado após marcar leitura.

### AC3 — Vínculo na criação e importação única de tickets antigos

**Given** um chamado novo aberto pelo FocoMEI
**When** a criação no ScrumHub for bem-sucedida
**Then** o vínculo `usuário/empresa → ticket` é persistido nesse momento
**And** o frontend persiste e usa o `id/url` retornado.

**Given** o usuário autenticado possui tickets antigos no ScrumHub no próprio e-mail
**When** ele solicita sincronizar/importar chamados antigos
**Then** a importação ocorre uma vez via `GET /public/tickets/meus?email=...`
**And** somente tickets do solicitante autenticado, usando e-mail/telefone confirmados do perfil
**And** cada ticket importado é validado como externo do projeto 39.

### AC4 — Polling idempotente a cada 5 minutos

**Given** não há webhook do ScrumHub
**When** o job backend executa
**Then** ele consulta tickets ainda não concluídos a cada 5 minutos via `GET /tickets-pai/:id` e `GET /public/tickets/:id/timeline?format=flat`
**And** há trava contra concorrência e tentativas limitadas
**And** somente diferenças novas geram evento, badge e WhatsApp
**And** chaves únicas por `scrumhub_ticket_id` e por evento remoto impedem WhatsApp e badges duplicados.

### AC5 — Conclusão do ticket

**Given** o poller detecta `status_id=127` ou `concluido=1`
**When** o evento de conclusão ainda não existe
**Then** é criado um único evento de conclusão
**And** o polling frequente daquele ticket para
**And** o app mostra notificação “Ticket concluído” e estado visual finalizado.

### AC6 — WhatsApp sem bloquear a sincronização

**Given** um comentário da equipe ou uma conclusão gera evento novo
**When** o backend tenta avisar por WhatsApp (padrão existente de envio outbound)
**Then** o aviso é enviado quando o canal estiver disponível
**And** a sincronização não falha nem é bloqueada se o canal estiver indisponível.

### AC7 — Autorização por vínculo local

**Given** uma leitura ou resposta de chamado
**When** o cliente envia um `ticketId`
**Then** o acesso é autorizado pelo vínculo local e pela identidade autenticada
**And** `ticketId` isolado nunca é prova de acesso
**And** respostas e logs não expõem API Key, payload técnico ou dados de chamados de outros solicitantes.

### AC8 — Central “Meus chamados” no app

**Given** o usuário autenticado na área de suporte das configurações
**When** ele abre “Meus chamados”
**Then** vê lista com código, assunto, status, prioridade, última atualização e badge de não lidos
**And** há estados vazio, erro e concluído.

### AC9 — Conversa do chamado

**Given** o usuário abre um chamado da lista
**When** a tela de conversa é exibida
**Then** mostra abertura + comentários em ordem
**And** há campo para responder
**And** a tela atualiza ao focar e faz polling leve enquanto estiver aberta
**And** o comentário enviado aparece somente após confirmação do backend.

### AC10 — Badge e aviso in-app de comentário da equipe

**Given** a sincronização persistiu um comentário novo da equipe
**When** o usuário está no app
**Then** há aviso in-app e badge de não lidos
**And** marcar como lido zera o badge correspondente àqueles eventos.

### AC11 — Verificação

**Given** a implementação concluída
**When** a suíte e a validação manual rodarem
**Then** o backend cobre testes de envelopes ScrumHub, ownership, importação legada, diff idempotente, comentário, conclusão e falha de WhatsApp
**And** o frontend cobre testes de lista, badge, leitura, conversa, resposta e estados vazio/erro/concluído
**And** passam `npm run lint`, `npm run typecheck`, `npm test` e `npm run build`
**And** o fluxo manual é validado: abrir chamado → comentar no ScrumHub → sincronizar → badge/WhatsApp → responder no FocoMEI → concluir no ScrumHub → notificação final.

## Escopo

### IN

- Rotação da API Key exposta e configuração somente em `SCRUMHUB_API_KEY` no backend.
- FocoMEI como intermediário; app nunca chama ScrumHub direto.
- Migration com vínculo/cache mínimo do ticket e eventos de notificação (leitura, comentário/conclusão, entrega WhatsApp), com unicidade por `scrumhub_ticket_id` e por evento remoto.
- Extensão do serviço ScrumHub para listar tickets do solicitante, detalhe/status, timeline e publicar comentário, normalizando envelopes `{ data }`.
- Rotas de suporte autenticadas: lista, detalhe/timeline, responder, marcar lidos + contador, sincronizar/importar antigos do próprio e-mail.
- Job/cron a cada 5 minutos, trava de concorrência, retries limitados, stop de polling frequente em ticket concluído (`status_id=127` ou `concluido=1`).
- WhatsApp via serviço outbound existente, sem bloquear sync.
- Tipos e chamadas no `supportService` (`SupportTicket`, `SupportTimelineItem`, `SupportNotification`).
- Modal de abertura existente permanece; persistir `id/url` após sucesso.
- Central “Meus chamados” em Configurações (suporte): lista, badge, conversa, resposta, estados vazio/erro/concluído.
- Testes backend/frontend e validação ponta a ponta descritos no plano.

### OUT

- Webhook do ScrumHub (não existe; não será criado no lado ScrumHub).
- Acesso direto do frontend à API ScrumHub.
- Armazenar o corpo completo dos comentários como fonte da verdade no banco FocoMEI.
- Alterar o fluxo de abertura além de persistir/usar `id/url` retornado.
- Expor API Key, payloads técnicos ou tickets de outros usuários.
- Qualquer feature não descrita no plano de origem.

## Dev Notes

- Arquitetura: User → Backend FocoMEI → (LocalDb vínculos/eventos + ScrumHub projeto 39). Job 5 min → ScrumHub + LocalDb. LocalDb alimenta badge/central e WhatsApp. Resposta do usuário: FocoMEI valida identidade e faz POST de comentário no ScrumHub.
- Persistência: guardar somente metadados necessários; timeline/comentários vêm do proxy ScrumHub.
- Novos tickets: vincular na criação. Legados: importação única `GET /public/tickets/meus?email=...` limitada ao autenticado.
- Sem webhook: só diffs novas geram evento, badge e WhatsApp.
- `@dev` não altera AC, título, descrição ou escopo; atualiza checkboxes e File List.
